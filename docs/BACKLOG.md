# Отложенное

Не «когда-нибудь потом», а решения, которые уже приняты, но не реализованы.
Здесь лежит то, ради чего не хочется второй раз проводить тот же разбор.

---

## Владельцы сервисов — сделано

Реализовано: три источника (спека, аннотации Ingress, ручной ввод) с
разрешением по каждому полю, фильтр «без владельца», счётчик. См. README.

Осталось из первоначального плана: **страница-инструкция для команд** с
готовыми кусками кода под l5-swagger, Scribe, springdoc. Это определяет,
дойдёт ли дело до автоматических источников вообще: если каждой команде
разбираться самой, не заполнит никто. Заготовки — ниже.

### Заготовки для инструкции

**Laravel, l5-swagger / swagger-php.** Блок `info` объявляется один раз, обычно
в `app/Http/Controllers/Controller.php`:

```php
/**
 * @OA\Info(
 *     title="Profile API",
 *     version="1.0.0",
 *     x={"team": "profile", "repo": "https://gitlab.company.ru/backend/profile"},
 *     @OA\Contact(name=API_TEAM_NAME, email=API_TEAM_EMAIL)
 * )
 * @OA\ExternalDocumentation(url="https://gitlab.company.ru/backend/profile")
 */
```

Внутри аннотаций **нельзя вызывать `config()` или `env()`** — они вычисляются
статически. У l5-swagger для этого есть подстановка констант из
`config/l5-swagger.php`:

```php
'constants' => [
    'API_TEAM_NAME'  => env('API_TEAM_NAME',  'Команда Профиля'),
    'API_TEAM_EMAIL' => env('API_TEAM_EMAIL', 'profile-team@company.ru'),
],
```

Тогда значения приезжают из `.env`, а в CI можно подставить `CI_PROJECT_URL` —
адрес репозитория проставится сам.

**Laravel, Scribe** — без аннотаций, в `config/scribe.php`:

```php
'openapi' => ['enabled' => true, 'overrides' => [
    'info.contact.name'  => 'Команда Профиля',
    'info.contact.email' => 'profile-team@company.ru',
    'externalDocs.url'   => 'https://gitlab.company.ru/backend/profile',
]],
```

Синтаксис `overrides` менялся между мажорными версиями Scribe.

**Аннотации на Ingress** — если PHP-код править не хотят:

```yaml
spectra.io/team: "Команда Профиля"
spectra.io/contact: profile-team@company.ru
spectra.io/repo: https://gitlab.company.ru/backend/profile
spectra.io/owners: ivanov,petrov
```

## Известные пробелы

**Вернувшийся сервис в журнале сканирований.** Сервис, пропавший из кластера и
появившийся снова, показывается как «изменений нет»: он не новый (запись уже
есть), а признак `present` меняется молча. Нужен третий список — «вернулись».
Правится в `SyncDiscovered`: до upsert собрать ключи с `present = false`, после
— пересечь с найденными.

**Слияние дублей.** Портал только помечает записи с общим публичным адресом.
Автоматически выбирать «настоящую» пробовали и откатили: надёжного признака
нет, а признак по числу ревизий переворачивал выбор сам собой. Если возвращать
— то с явным подтверждением человека и без скрытия того, что он не подтвердил.

**Ручной опрос не разведён с плановым.** `PollDue` защищён мьютексом от
наложения свипов, но опрос одного сервиса по кнопке идёт мимо него. Если
нажать «Опросить сейчас» во время свипа, оба опросят один сервис, и запись
результата сделает тот, кто закончил последним — с более старым временем
проверки. Видно только на глаз в поле «проверено»; данные не портятся. Правится
блокировкой на сервис в коллекторе. Замечено при проверке запасного адреса на
кластере.

**Пайплайн CI.** Тесты и сборка образа запускаются руками. `make test`
поднимает одноразовый Postgres сам, так что перенести это в пайплайн —
несколько строк.

**Уведомления о ломающих изменениях** (Slack, почта). Данные готовы: признак
`breaking` лежит в таблице `changes`.

**Поиск по эндпоинтам через все сервисы.** Требует индекса операций в базе —
сейчас он строится в памяти при сравнении.

**Аутентификация сложнее Basic.** Предполагается SSO впереди портала.

## RabbitMQ — отложенное

**Контракты сообщений: AsyncAPI.** Для REST сервисы ведут OpenAPI, и Spectra
его находит, хранит ревизии и показывает ломающие изменения. Для сообщений то
же самое делает AsyncAPI — стандарт, а не свой формат: каналы (exchange и
очереди с привязками AMQP), операции «отправляет / получает», схемы payload.
Решено вести его, а не самописный список связей (первый вариант этого пункта
предлагал `.spectra/messaging.yaml` — отказались: команды учили бы формат
Spectra, а контракт сообщений в нём не помещался).

1. **Формат — AsyncAPI 3.0 с привязками `amqp`.** Чего стандарт не описывает —
   способ чтения — идёт расширением `x-spectra-mode`
   (`subscribe | schedule | get | manual`): это то, что снимок брокера не видит.

   ```yaml
   asyncapi: 3.0.0
   info: { title: documents-archiver, version: 1.4.2 }
   channels:
     signed:
       address: documents.notify
       bindings:
         amqp: { is: queue, queue: { name: documents.notify, vhost: documents } }
       messages:
         documentSigned: { $ref: '#/components/messages/DocumentSigned' }
   operations:
     readSigned:
       action: receive
       channel: { $ref: '#/channels/signed' }
       x-spectra-mode: schedule
       description: CronJob, каждую ночь в 03:00
   components:
     messages:
       DocumentSigned:
         payload:
           type: object
           required: [documentId]
           properties: { documentId: { type: string } }
   ```

2. **Где Spectra его берёт — как OpenAPI.**
   - У HTTP-сервисов — по конвенциональным путям рядом с поиском спеки:
     `/asyncapi.json`, `/asyncapi.yaml`, `/asyncapi/asyncapi.json` (так отдаёт
     Saunter для .NET); ручной адрес — аннотацией `spectra.io/asyncapi-url`.
   - У воркеров и CronJob, которым нечего отдавать по HTTP, — файл
     `asyncapi.yaml` в корне репозитория, через API GitLab на ту версию, что
     задеплоена (лейбл `app.kubernetes.io/version`). Нужны `SPECTRA_GITLAB_URL`
     и токен только на чтение.

3. **Что Spectra с ним делает.**
   - Ревизии по хэшу нормализованного документа и дифф, как у спек. Ломающее:
     удалён канал или операция, в сообщении удалено обязательное поле или
     сменился тип, появилось обязательное поле в том, что сервис получает.
   - Связи из операций пишет в `mq_declared` с отдельным источником (сейчас там
     заготовлен `code` — переименовать в `asyncapi`) и для каждого сервиса
     заменяет их целиком при новой ревизии.
   - Просмотр — вендоренный `@asyncapi/react-component`, как Scalar для OpenAPI.

4. **CI-агент — помощник, а не источник правды.**
   - Один раз генерирует первые `asyncapi.yaml` по коду и аудиту
     (`contracts.rabbitmq` в `audit/inventory.json`), одним MR на репозиторий.
   - Дальше в каждом MR: `asyncapi validate` и сверка с кодом. Код публикует в
     exchange, которого нет в документе, или документ обещает очередь, которую
     код не читает, — предупреждение и комментарий в MR, а не правка файла.
     Поиск по коду: `amqp091-go`, `RabbitMQ.Client` / MassTransit,
     `php-amqplib`, Laravel queue и Symfony Messenger в конфигах, плюс
     внутренняя LLM — разрешить имена из конфигов и env, понять способ чтения
     (CronJob → `schedule`).

5. **Три источника у каждой связи** — «видно в брокере», «по контракту»,
   «вручную» — и сверка между ними. «По контракту читает по расписанию, в
   брокере не видно» — норма. «В брокере видно, в контракте нет» — гигиена:
   незаявленная связь.

6. **Цена.** Документ надо вести, как Swagger, а генераторы AsyncAPI слабее,
   чем OpenAPI: для .NET есть Saunter, для Go и PHP почти ничего — там документ
   чаще пишут руками. Без агента на старте и проверки в CI документы устареют.

**Kafka.** Та же модель: топики, consumer groups и их lag через Admin API,
сервис — по `client.id` и `group.id`. Если есть Schema Registry — история схем
с режимом совместимости, как у спек.

**Сообщения в очередях — не делаем (решено).** Глубина очередей, скорости,
lag — это мониторинг, а Spectra — каталог. Первая версия показывала число
сообщений и опрашивала брокер раз в 5 минут; убрано: раздел смещался от «что
есть и кто с чем связан» к «что сейчас происходит». Если понадобится — ссылка
из карточки очереди на её дашборд в Grafana, а не цифра в Spectra.

**Публикующие без detailed-статистики.** Брокер в режиме по умолчанию не
говорит, кто публикует. Обходной путь — тот же список из кода (см. выше).

**Проверено только на 3.13.** Поля ответов Management API сверены на живом
брокере 3.13 в обоих режимах статистики. На 3.12 и 4.x стоит прогнать
`internal/rabbitmq/live_test.go` перед внедрением.
