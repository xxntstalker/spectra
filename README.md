# API Portal

Одна точка входа во все Swagger/OpenAPI сервисы: список сервисов, их
спецификации, дата последнего изменения контракта и лента «что изменилось».

## Задача

Сервисов много, у большинства свой Swagger по своему адресу. Живущий с этим
человек упирается в три вещи:

- **Где смотреть.** Адреса расходятся по вики, чатам и памяти. Нового человека
  в команде нужно водить за руку.
- **Актуально ли.** Открыв чужой Swagger, невозможно понять, это контракт
  недельной давности или полугодовой.
- **Что изменилось.** О сломанном контракте узнаёшь от упавшей интеграции, а не
  от того, кто его сломал.

Портал закрывает все три: адрес один, у каждого сервиса стоит честная дата
последнего изменения контракта, и есть лента с расшифровкой, что именно
поменялось.

## Возможности

- **Автопоиск спеки.** В реестре достаточно `baseUrl`. Портал перебирает 31
  конвенциональный путь (Spring, ASP.NET, FastAPI, DRF, Laravel, Symfony,
  NestJS, Fastify, Quarkus, Rails и др.), а если не нашёл — читает HTML-страницу
  документации и достаёт адрес оттуда.
- **Честная дата обновления.** Ревизия записывается по смене хэша
  нормализованной спеки, а не по факту опроса.
- **История ревизий.** Любую прошлую версию спеки можно открыть и почитать —
  например, чтобы посмотреть, как API выглядел до деплоя.
- **Лента изменений** с расшифровкой на уровне эндпоинтов: добавлен параметр,
  убран ответ, изменилась общая схема.
- **Пометка ломающих изменений** — удалённый эндпоинт, новый обязательный
  параметр и т.п.
- **Статус доступности** каждого сервиса, с разделением «сервис лежит» и
  «сервис жив, но спеки не отдаёт».
- **Встроенный вьюер** спецификаций, работает офлайн.
- **Try it out** через прокси портала — снимает CORS и достаёт до сервисов,
  недоступных браузеру напрямую.
- **Поиск** по сервисам, тегам и группам.
- **HTTP API** на всё вышеперечисленное.

## Форматы

Работает со Swagger 2.0, OpenAPI 3.0 и 3.1, в JSON и в YAML — в одном реестре
и вперемешку. Разница форматов спрятана внутри: сервисы сравниваются и
диффаются одинаково независимо от того, на чём написаны.

Что для этого делается:

| | |
|---|---|
| `#/definitions/…` (2.0) и `#/components/schemas/…` (3.x) | разрешаются одним механизмом |
| Тело запроса: параметр `in: body`/`formData` (2.0) против `requestBody` (3.x) | приводятся к одному виду, поэтому сравнимы между форматами |
| Адрес: `host`+`basePath`+`schemes` (2.0) против `servers` (3.x) | одинаково выбрасываются при хэшировании и одинаково переписываются на прокси |
| `webhooks` (3.1) | индексируются наравне с `paths` |
| `$ref` рядом с другими полями (3.1) | поддерживается |

**Смена формата сервисом** (апгрейд фреймворка, 2.0 → 3.0) отмечается заметкой
«версия OpenAPI: 2.0 → 3.0.3» и **не помечается ломающей**. Совсем без шума не
обходится: описание одного и того же API в двух форматах устроено по-разному,
поэтому эндпоинты попадут в ленту как «изменилась схема данных или описание».
Убрать это можно было бы только полноценным конвертером 2.0 → 3.0, и на такое
портал не претендует.

## Быстрый старт

Нужен только Docker. Ничего настраивать не надо:

```bash
make demo-up
```

Портал — на <http://localhost:8080>. Поднимутся сам портал и семь фейковых
сервисов, публикующих спеки семью разными способами; через минуту в ленте
появятся первые изменения.

Остановить и убрать данные:

```bash
make demo-down
```

На своих сервисах:

```bash
cp services.example.yaml services.yaml   # вписать свои сервисы
make up
```

# Почему так сделано (ADR)

Решения, о которых стоит знать до того, как что-то менять. Каждое чем-то
оплачено — цена указана.

### 1. Свой агрегатор, а не готовое решение

Рассматривались: голый Swagger UI со списком `urls` (полчаса работы, но ни дат,
ни истории, ни статусов — тупик), Backstage (правильный дом для этого, если
каталог сервисов уже есть; иначе инфраструктуры на порядок больше самой
задачи), Apicurio Registry (версионирование есть, но заточен под push),
SwaggerHub (платный).

**Почему:** задача маленькая и с чёткими границами, а готовые решения либо не
дают истории, либо тянут за собой много лишнего.
**Чем платим:** это свой код, его надо поддерживать.

### 2. Pull, а не push

Портал сам ходит за спеками; сервисы о нём не знают.

**Почему:** push требует править CI или код каждого сервиса — на десятках
команд это не взлетает. Pull подключает сервис одной строкой в реестре.
**Чем платим:** портал должен иметь сетевой доступ ко всем сервисам, и спека
обновляется с задержкой до одного интервала опроса.

### 3. Автопоиск пути к спеке

**Почему:** `/swagger` — это HTML-страница, а не спека, и настоящий путь
зависит от фреймворка. Заставлять человека выяснять его для каждого сервиса —
ровно тот ручной труд, ради устранения которого портал и делается.
**Чем платим:** список путей ручной и его надо пополнять. Стоимость перебора
близка к нулю: адрес кэшируется, отказ в соединении мгновенный.

### 4. Реестр — файл в git, а не автодискавери из Kubernetes

**Почему:** файл живёт в git, изменения проходят ревью, добавление сервиса —
однострочный diff. Автодискавери требует доступа к kube API, RBAC и разметки
чужих манифестов.
**Чем платим:** новый сервис не появляется сам. Дискавери из k8s — очевидное
следующее расширение, точка расширения одна ([internal/config](internal/config/config.go)).

### 5. Ревизия по хэшу нормализованной спеки

Спека нормализуется (сортировка ключей объектов и порядконезависимых массивов,
выброшенные `servers`/`host`/`basePath` и поля из `ignoreFields`), берётся
sha256, ревизия пишется только при смене хэша.

**Почему:** опрос — не обновление. Без этого «обновлено» означало бы «мы
недавно спрашивали», то есть ничего. Нормализация отсекает то, что меняется
от пересборки к пересборке, не меняя контракта.
**Чем платим:** остаточный шум всё равно возможен — генератор, который пишет
в спеку что-то своё за пределами `ignoreFields`, даст ревизию.

### 6. Дифф с развёрнутыми `$ref`

Операции хэшируются с рекурсивно подставленными локальными `$ref`.

**Почему:** правка общей схемы в `components` не меняет объект операции, но
меняет контракт каждого эндпоинта, который на неё ссылается. Буквальное
сравнение операций такое изменение не заметит вовсе — а это самый частый вид
изменения в реальных спеках.
**Чем платим:** одна правка популярной схемы даёт много «изменённых»
эндпоинтов. Это правда, а не шум, но лента от неё разрастается.

### 7. Своя эвристика ломающих изменений вместо oasdiff

**Почему:** oasdiff — внешний бинарник в рантайме. Ради «привлечь внимание»
это лишняя зависимость; своя проверка укладывается в один файл.
**Чем платим:** покрытие заведомо неполное — семантику и ужесточение валидации
внутри схемы она не ловит. Как гейт в CI не годится; для этого берите
[oasdiff](https://github.com/Tufin/oasdiff).

### 8. SQLite

**Почему:** пара десятков сервисов и сотни ревизий; всё помещается в один файл,
который тривиально бэкапить, и портал остаётся деплоем из одного бинарника без
отдельной СУБД рядом.
**Чем платим:** одна реплика. Горизонтально портал не масштабируется — при
такой нагрузке это и не нужно.

### 9. Вьюер завендорен, а не с CDN

**Почему:** портал предназначен для внутренней сети, где выход на CDN часто
закрыт. Документационный портал, которому для показа документации нужен
публичный интернет, — плохой портал.
**Чем платим:** ~2,7 МБ в репозитории и ручное обновление (`make vendor-viewer`).

### 10. Спеки отдаются из своей БД, а не редиректом на сервис

**Почему:** снимает CORS, и документация читается даже когда сервис лежит.
**Чем платим:** видно последнюю собранную ревизию, а не то, что сервис отдаёт
прямо сейчас (расхождение — не более интервала опроса).

# Безопасность

## Главное

**У портала нет собственной аутентификации.** Он не проверяет, кто пришёл.

При `proxy: true` портал проксирует запросы к вашим внутренним API и становится
точкой доступа к ним. Выставлять его наружу можно **только** за
SSO/ingress-авторизацией. Если такой обвязки нет — оставьте `proxy: false`,
и портал будет read-only витриной спецификаций.

## Что уже сделано

- **Прокси не может стать открытым релеем.** Адрес назначения берётся
  исключительно из конфига; путь в URL лишь выбирает заранее зарегистрированный
  сервис. Произвольный адрес подставить нельзя.
- **Cookie портала не уходят наверх** — сессия портала не утекает в сервисы.
  Заголовки из конфига перекрывают присланные браузером.
- **Внешние `$ref` не разрешаются.** Портал читает спеки многих чужих сервисов
  и не должен ходить по URL, которые в них написаны. Такие ссылки остаются
  маркером в структуре.
- **Кандидаты дискавери фильтруются по хосту.** В шаблоне Swagger UI по
  умолчанию прописан публичный petstore, и без этой проверки портал
  заагрегировал бы его вместо вашего сервиса.
- **Размер ответа ограничен 8 МиБ** — ошибочный адрес не утянет в память
  безразмерный поток.
- **Токены — через окружение** (`${VAR}` в `headers`), а не в файле, который
  лежит в git.
- **Контейнер** — distroless, без shell, непривилегированный пользователь,
  статический бинарник.
- **Содержимое чужих спек не исполняется.** Собственный UI портала экранирует
  всё, что пришло из спеки. Вьюер проверен точечно: `<img onerror=…>` в
  `info.description` рендерится как тег, но обработчик вырезается и код не
  выполняется. Это одна проба, а не пентест, — но очевидный вектор закрыт.

## Что стоит сделать перед продом

- Закрыть портал авторизацией (oauth2-proxy, ingress-auth, что у вас принято).
- Решить, нужен ли `proxy` вообще — без него поверхность заметно меньше.
- Ограничить сетевой доступ портала до списка сервисов из реестра.

# Разработка

## Что нужно

Запускать приложение можно только докером — Go нужен, чтобы менять код.

Go 1.25 и больше ничего: SQLite здесь на чистом Go (`modernc.org/sqlite`), CGO
не нужен, фронтенд без сборки, вьюер спецификаций завендорен в репозиторий.

```bash
make test
```

Собранные бинарники в репозиторий не кладутся: `bin/` и `data/` в `.gitignore`,
в контекст сборки образа не попадают.

## Демо-стенд

Демо отделено от сервиса: живёт в [demo/](demo/), в прод-образ не попадает и не
компилируется при его сборке.

Проще всего целиком в докере — `make demo-up` (см. «Быстрый старт»). Без докера,
в двух терминалах:

```bash
go run ./demo -mutate-interval 45s
```

```bash
make run
```

Поднимаются семь фейковых сервисов, каждый публикует спеку по-своему:

| Сервис | Порт | Где спека | Как находится |
|---|---|---|---|
| orders | 7101 | `/v3/api-docs` | перебор (Spring) |
| billing | 7102 | `/swagger/v1/swagger.json` | перебор (ASP.NET) |
| inventory | 7103 | `/openapi.json` | перебор (FastAPI) |
| notifications | 7104 | `/internal/contracts/notifications-v1.json` | со страницы `/swagger` (Redoc `spec-url`) |
| legacy-payments | 7105 | `/v2/api-docs`, Swagger 2.0 | явно в конфиге |
| analytics | 7106 | `/openapi.yaml`, YAML | перебор |
| warehouse | 7107 | `/internal/openapi-v3` | со страницы `/swagger` → `configUrl` → список спек |

Восьмой сервис в реестре (`shipping`) намеренно не запускается — так выглядит
недоступный.

Страница `/swagger` у notifications содержит забытый в шаблоне публичный
petstore. Это не мусор, а проверка: портал обязан его проигнорировать, иначе
вместо вашего сервиса он заагрегирует чужой API.

Поменять контракт руками и посмотреть на ленту изменений:

```bash
curl -X POST localhost:7103/_demo/mutate
```

Дальше — «Опросить все» в портале. Впрочем, демо и само крутит мутации каждые
45 секунд, так что лента наполняется без вмешательства.

## Структура

```
cmd/portal            бинарь портала
internal/config       чтение реестра
internal/discovery    поиск спеки: перебор путей + разбор страницы документации
internal/openapi      разбор, канонизация, хэш, индекс операций, дифф
internal/collector    опрос по расписанию, запись ревизий
internal/store        SQLite
internal/api          HTTP API, прокси, отдача UI
internal/web          встроенный UI + вендоренный вьюер (Scalar)
demo/                 демо-стенд: фейковые сервисы, свой Dockerfile и compose
```

Зависимости: `modernc.org/sqlite` и `gopkg.in/yaml.v3`. Всё.

## Как находится спецификация

`/swagger` — это HTML-страница, а не спека, и лежит она в каждом фреймворке
по-своему. Поэтому [discovery](internal/discovery/discovery.go) идёт в три шага:

1. **Явный путь из конфига** (`specUrl`), если задан.
2. **Перебор 31 конвенционального пути**: Spring, ASP.NET, FastAPI, DRF,
   Laravel (l5-swagger, Scribe), Symfony (Nelmio, API Platform), NestJS,
   Fastify, Express, Quarkus, MicroProfile, Rails, Grape, utoipa, swaggo и др.
   Ответ принимается, только если разбирается как OpenAPI, — health-check на
   `/api-docs` спекой не станет.
3. **Чтение страницы документации** (14 вариантов: `/swagger`, `/docs`,
   `/api/documentation`, `/redoc`, …) и извлечение адреса спеки из неё:
   `spec-url` у Redoc, `data-url` у Scalar, `url:` у Swagger UI, а у springdoc —
   `configUrl`, по которому лежит уже список спек.

Кандидаты с чужого хоста отбрасываются — см. про petstore выше.

Длинный список путей ничего не стоит: адрес запоминается в БД, перебор
происходит один раз, а отказ в соединении возвращается мгновенно. Если
запомненный адрес перестал отвечать, портал забывает его и ищет заново —
сервисы переезжают при смене фреймворка.

## Как считается «последнее обновление» и дифф

Зачем именно так — см. ADR [5](#5-ревизия-по-хэшу-нормализованной-спеки) и
[6](#6-дифф-с-развёрнутыми-ref). Механика:

1. Спека нормализуется в [openapi/spec.go](internal/openapi/spec.go): ключи
   объектов сортируются, при `ignoreServers` выбрасываются
   `servers`/`host`/`basePath`/`schemes`, удаляются поля из `ignoreFields`,
   и сортируются массивы, где порядок не значим (`required`, `enum`, `tags`,
   `parameters`, `security`).
2. От результата берётся sha256. Совпал с хэшем последней ревизии — ничего не
   пишем, только отмечаем время проверки.
3. Не совпал — пишем ревизию (её дата и есть «обновлено») и считаем дифф с
   предыдущей.
4. Дифф в [openapi/diff.go](internal/openapi/diff.go) сравнивает операции по
   ключу `METHOD /path` и по хэшу операции **с развёрнутыми локальными `$ref`**.
   В демо это видно: одно поле, добавленное в схему `Item`, даёт три
   изменённых эндпоинта — ровно те, что на неё ссылаются.
5. Расхождения раскладываются на коды (`param.added.required`,
   `response.removed.success`, …). Формулировки живут в UI
   ([app.js](internal/web/static/app.js)), бэкенд отдаёт только коды.

Ломающими помечаются: удалённый эндпоинт, удалённый успешный (2xx) ответ,
новый обязательный параметр, параметр, ставший обязательным, и новое
обязательное поле в теле запроса.

### Если сервис перегенерирует спеку на каждом билде

Частый случай: контракт не менялся, а спека каждый раз выходит другой. Что
портал с этим делает:

| Что меняет генератор | |
|---|---|
| Порядок ключей в объектах | нормализуется всегда |
| Порядок в массивах (`required`, `enum`, `tags`, …) | нормализуется всегда |
| Адрес сервиса (`servers`/`host`) | `ignoreServers: true` (по умолчанию) |
| Версия сборки в `info.version` | `ignoreFields: [info.version]` |
| Таймштамп в `info.description` | `ignoreFields: [info.description]` |

Первые две строки закрыты по умолчанию и настройки не требуют — генераторы,
собирающие спеку рефлексией, регулярно выдают массивы в непредсказуемом
порядке. Последние две включаются осознанно: выбросив `info.version`, вы
перестанете видеть и настоящие смены версии API.

Симптом, что настройка нужна: сервис «обновляется» на каждый деплой, а в
изменениях — только «изменилась схема данных или описание».

# Разворот

Приложение раскатывается только контейнером. Собранных бинарников в репозитории
нет и быть не должно — образ собирается из исходников.

## docker compose

Положите рядом свой `services.yaml` (шаблон —
[services.example.yaml](services.example.yaml)) и:

```bash
make up      # docker compose up --build -d
make logs
make down
```

`make up` заранее проверяет, что `services.yaml` существует: для отсутствующего
файла Docker молча создаёт на его месте каталог, и портал падает с невнятным
«is a directory».

## docker run

Если compose не используется:

```bash
docker build -t api-portal:latest .
```

```bash
docker run -d --name api-portal \
  -p 8080:8080 \
  -v "$PWD/services.yaml:/etc/api-portal/services.yaml:ro" \
  -v api-portal-data:/data \
  api-portal:latest
```

## Про образ

Distroless, статический бинарник, **~16 МБ**, непривилегированный пользователь
(uid 65532). UI и вьюер спецификаций вшиты внутрь — рядом с контейнером не
нужно ничего, кроме реестра.

Реестр в образ не вшит: он у каждого свой и меняется чаще, чем код. База лежит
в томе `/data`; том переживает пересоздание контейнера, а `down -v` его удаляет.

В образе нет shell, поэтому `HEALTHCHECK` использует собственный режим
бинарника (`portal -health-check`). Снаружи то же самое доступно как
`GET /healthz` — он проверяет портал, а не опрашиваемые сервисы: лежащий
сервис это штатная ситуация и выводить портал из ротации не должен.

## Конфигурация

Скопируйте [services.example.yaml](services.example.yaml) в `services.yaml`:

```yaml
listen: ":8080"
database: /data/portal.db

poll:
  interval: 1h         # спека меняется на деплое, а не поминутно
  timeout: 10s         # таймаут одного запроса
  budget: 2m           # бюджет на весь опрос сервиса (автопоиск — до 45 запросов)
  maxBackoff: 6h       # потолок паузы для стабильно падающего сервиса
  concurrency: 8

retention:
  versions: 100        # сколько ревизий спеки хранить на сервис

defaults:
  ignoreServers: true
  ignoreFields: []     # напр. [info.version] — если генератор пишет туда сборку
  proxy: false

services:
  - id: orders                       # обязателен, уникальный, URL-safe
    baseUrl: http://orders.internal  # обязателен
    name: Orders                     # по умолчанию = id
    group: Commerce                  # группа в левом меню
    tags: [core]

  - id: legacy
    baseUrl: http://legacy.internal
    specUrl: /v2/api-docs            # если автопоиск промахнулся
    headers:
      Authorization: "Bearer ${LEGACY_TOKEN}"   # подстановка из окружения
```

`ignoreServers`, `ignoreFields` и `proxy` задаются в `defaults` и перекрываются
на отдельном сервисе.

**Адреса проверяются при старте.** `baseUrl: orders.internal` без схемы —
частая опечатка, которая иначе всплыла бы позже как «сервис не отвечает».
Портал откажется стартовать и скажет, что чинить.

**Бюджет должен быть заметно больше таймаута.** Автопоиск делает до 45
запросов; если `budget` равен `timeout`, медленный, но живой сервис не
найдётся никогда — дедлайн истечёт на середине перебора.

**Неудачный опрос разрежается.** Пауза удваивается от `interval` до
`maxBackoff`, кнопка «Опросить» её сбрасывает. Без этого сервис без спеки
получал бы 45 запросов каждый интервал бесконечно.

**Реестр читается только при старте.** После правки `services.yaml`:

```bash
docker compose restart portal
```

Кнопка «Опросить все» перечитывает спеки, а не конфиг.

## Флаги

В контейнере задаются как аргументы: `command: ["-config", "...", "-log", "debug"]`
в compose или после имени образа в `docker run`.

| Флаг | |
|---|---|
| `-config` | путь к реестру (по умолчанию `services.yaml`) |
| `-listen` | перебить адрес из конфига |
| `-db` | перебить путь к базе |
| `-log` | `debug`, `info`, `warn`, `error` |
| `-health-check` | опросить свой же `/healthz` и выйти 0/1 |

Находки дискавери (`discovered spec ... via=probe`) пишутся на уровне `info` —
это самое полезное при разборе проблем с новым сервисом. `-log debug` добавляет
лог всех запросов к API и прокси.

## Эксплуатация

Всё состояние — один файл SQLite в томе `/data`.

**Бэкап.** Копировать файл на ходу нельзя: рядом лежит WAL, и копия может
оказаться полузаписанной. Остановите контейнер на пару секунд:

```bash
docker compose stop portal
docker compose cp portal:/data/portal.db ./portal-backup.db
docker compose start portal
```

**Стереть историю** — удалить том вместе с контейнерами: `docker compose down -v`
(для демо — `make demo-down`).

**Обновить вьюер** — `make vendor-viewer`. Он завендорен специально: портал
должен работать во внутренней сети без выхода на CDN.

# Использование

## Интерфейс

- **Левое меню** — сервисы по группам, цветная точка = статус, под именем
  «обновлено N назад». Поиск сверху фильтрует по имени, id, заголовку спеки,
  группе и тегам.
- **«Последние изменения»** (стартовая) — общая лента по всем сервисам,
  ломающие изменения помечены красным.
- **Страница сервиса → «Спецификация»** — встроенный вьюер. Спека отдаётся из
  базы портала, поэтому читается даже когда сервис лежит.
- **→ «История и изменения»** — все зафиксированные изменения с расшифровкой и
  таблица ревизий. Из таблицы открывается любая старая ревизия — удобно, когда
  надо посмотреть, как API выглядел до деплоя.
- **«Опросить» / «Опросить все»** — внеочередной опрос, не дожидаясь тика.

Статусы и даты обновляются сами раз в 15 секунд, при этом вьюер не
перезагружается — позиция прокрутки в спеке не теряется.

## Добавить сервис

Одна запись в `services.yaml` — и перезапуск портала:

```yaml
  - id: orders
    baseUrl: http://orders.internal
    group: Commerce
    tags: [core]
```

Путь к спеке указывать не нужно.

Сервис, убранный из конфига, из базы не удаляется — пропадает из UI, но история
ревизий сохраняется и вернётся вместе с ним.

## Если сервис не подхватился

Статус в UI различает два разных случая:

| Статус | Что значит | Что делать |
|---|---|---|
| `недоступен` | никто не ответил ни на один адрес | сеть, порт, сервис лежит |
| `спека не найдена` | сервис отвечает, но OpenAPI нигде нет | указать `specUrl` вручную |
| `спека не разбирается` | по адресу что-то есть, но это не OpenAPI | проверить, что отдаёт сервис |

Проверить руками:

```bash
curl -s http://orders.internal/v3/api-docs | head -c 300
```

Нашли адрес — пропишите явно, и перебор прекратится:

```yaml
  - id: orders
    baseUrl: http://orders.internal
    specUrl: /internal/openapi-v3     # путь или полный URL
```

Если ваш фреймворк публикует спеку по адресу, которого нет в списке
кандидатов, — это стоит починить в
[discovery.go](internal/discovery/discovery.go), а не в конфиге каждого сервиса.

## Try it out

При `proxy: true` портал переписывает `servers` в отдаваемой спеке на
`/proxy/<id>` и проксирует запросы к сервису. Это снимает CORS и позволяет
работать с сервисами, до которых у браузера пользователя нет прямого доступа.
Про безопасность — см. раздел «Разворот».

## HTTP API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/healthz` | здоровье портала |
| GET | `/api/services` | список сервисов со статусом и датой обновления |
| GET | `/api/services/{id}` | сервис + ревизии + изменения |
| GET | `/api/services/{id}/spec` | последняя спека (`?version=N` — конкретная ревизия) |
| GET | `/api/changes` | лента изменений (`?service=`, `?limit=`) |
| POST | `/api/refresh` | внеочередной опрос (`?service=`) |

Спека всегда отдаётся как JSON, даже если сервис публикует YAML.

## Чего пока нет

- Аутентификации; см. предупреждение выше.
- Поиска по эндпоинтам через все сервисы — заметная дыра, но требует индекса
  операций в БД (сейчас индекс строится в памяти при сравнении).
- Уведомлений о ломающих изменениях (Slack/почта). Данные готовы: `breaking`
  лежит в таблице `changes`.
- Метрик (`/metrics`) — есть только `/healthz` и логи.
- Перечитывания реестра без рестарта.
- Линтинга спек (Spectral) и авто-дискавери сервисов из Kubernetes — реестр
  сейчас только из файла.
