# Spectra

Одна точка входа во все Swagger/OpenAPI сервисы кластера: список адресов,
спецификации, честная дата последнего изменения контракта и лента «что
изменилось».

Список сервисов Spectra берёт из объектов Ingress — вести его вручную не нужно.

**Быстро посмотреть** (нужен только Docker):

```bash
make demo-up
```

<http://localhost:8080>, логин `admin` / `admin`. Поднимутся сама Spectra,
Postgres и семь фейковых сервисов, публикующих спеки семью разными способами.

# 1. Что это и как работает

## Задача

Сервисов много, у большинства свой Swagger по своему адресу. Человек, который с
этим живёт, упирается в три вещи:

- **Где смотреть.** Адреса расходятся по вики, чатам и памяти.
- **Актуально ли.** Открыв чужой Swagger, невозможно понять, это контракт
  недельной давности или полугодовой.
- **Что изменилось.** О сломанном контракте узнаёшь от упавшей интеграции.

## Возможности

- **Список из кластера.** Читает `Ingress` во всех namespace. Ingress-контроллер
  не нужен: Spectra только читает объекты, а запросы шлёт в backend-сервисы.
- **Автопоиск спецификации.** Сначала читает HTML-страницу документации и
  достаёт адрес оттуда, потом перебирает 31 конвенциональный путь.
- **Честная дата обновления.** Ревизия пишется по смене хэша нормализованной
  спеки, а не по факту опроса.
- **История ревизий** — любую прошлую версию можно открыть и почитать.
- **Лента изменений** с расшифровкой на уровне эндпоинтов, пометкой ломающих и
  распознаванием откатов.
- **Владелец сервиса** — команда, контакт, ссылка на исходники, люди.
- **Группы и теги** — свести несколько сервисов в «Профиль и авторизация».
- **Хост без API — нормально.** Такой сервис можно спрятать, и Spectra
  перестанет его трогать.
- **Ручной адрес спеки** там, где автопоиск промахнулся.
- **Try it out** через прокси (по умолчанию выключен). Пока прокси выключен
  или читатель не вошёл, кнопка отправки запроса не показывается: отправлять
  всё равно некуда.
- **Самоподписанные сертификаты** — свой корневой сертификат через
  `SPECTRA_CA_BUNDLE` либо отключение проверки через `SPECTRA_TLS_SKIP_VERIFY`.
- **Метрики** `/metrics` в формате Prometheus и `/healthz`.

Работает со Swagger 2.0, OpenAPI 3.0 и 3.1, в JSON и в YAML, вперемешку.

## Откуда берутся сервисы

Раз в час Spectra читает `Ingress` во всех namespace — это тот же вызов API, что
делает `kubectl get ing -A`. Из каждого правила получается кандидат: публичный
хост для показа, backend-сервис для опроса.

Опрос идёт в `svc.namespace:port`, а не в публичный хост: изнутри кластера такой
хост часто не резолвится или уходит на внешний балансировщик и возвращается
обратно. Переключается через `SPECTRA_K8S_TARGET`.

Второй адрес при этом не выбрасывается, а остаётся запасным. Если основной не
отвечает — NetworkPolicy между namespace, переименованный Service, порт,
открытый только ingress-контроллеру — Spectra повторяет попытку по публичному
хосту, и сервис не помечается упавшим. Сработавший адрес запоминается и в
следующий раз пробуется первым; ближайшее сканирование кластера сбрасывает это
предпочтение, давая основному адресу новый шанс после починки сети. Если не
ответили оба, в ошибке перечислены оба — чтобы не выяснять отдельно, пробовали
ли публичный.

Запасной адрес не спасает от «сервис ответил, а спеки нет»: на такой ответ
второй адрес не опрашивается — ответ будет тот же, а запросов к чужому сервису
станет вдвое больше.

Отсеиваются ACME-челленджи cert-manager, wildcard-хосты, исключённые namespace
и всё с аннотацией `spectra.io/skip`. Два Ingress на один backend — это один
API, они схлопываются.

Ключ группировки — хост **и префикс пути правила**. Один хост с путями
`/orders/(.*)` и `/billing/(.*)` — это два разных API, они маршрутизируются по
пути и дублями не считаются.

Обратный случай — несколько Ingress на один хост и **один и тот же** путь —
помечается, но не схлопывается. Снаружи это один адрес, и ingress-
контроллер направляет его ровно в один backend, так что рабочей записью, скорее
всего, является одна. Но какая именно, порталу неоткуда знать: он показывает
обеим записям пометку «возможный дубль», ссылку друг на друга и основание, а
решает человек — кнопкой «спрятать». Схлопывать пробовали; признак выбора
включал число ревизий, оно росло, и победитель переворачивался сам собой —
записи пропадали из списка без единого изменения в кластере.

Название сервиса берётся из спецификации (`info.title`): имя backend-Service по
кластеру повторяется десятками — «api», «web», «backend». Имя, объявленное
аннотацией `spectra.io/name` или вписанное в интерфейсе, не уступает ничему.

## Как находится спецификация

1. **Ручной адрес** или аннотация `spectra.io/spec-url`, если заданы.
2. **Страница документации** (14 вариантов: `/swagger`, `/docs`,
   `/api/documentation`, `/redoc`…) — из неё достаётся адрес спеки: `spec-url`
   у Redoc, `data-url` у Scalar, `url:` у Swagger UI, `configUrl` у springdoc.
3. **Перебор 31 конвенционального пути**: Spring, ASP.NET, FastAPI, DRF,
   Laravel, Symfony, NestJS, Fastify, Quarkus, Rails и другие.

Страница идёт первой намеренно: на реальной инфраструктуре JSON лежит по
адресам, которых нет ни в одной конвенции, а `/swagger` есть почти везде и
обязан сообщать своему вьюеру, где спека. Это два запроса вместо тридцати
промахов.

Кандидаты с чужого хоста отбрасываются: в шаблоне Swagger UI по умолчанию
прописан публичный petstore, и без проверки Spectra заагрегировала бы его.

## Когда опрос прекращается

| Что случилось | Что дальше |
|---|---|
| Спека собрана | опрос по расписанию, условными запросами (304) |
| **Сервис ответил, но спеки нет** | **автоматический опрос выключается совсем** |
| Сервис недоступен | остаётся в расписании, пауза удваивается до потолка |
| Спрятан вручную | не опрашивается никогда |

Хост без API сам по себе спеку не отрастит, поэтому перебирать по нему полсотни
путей раз в час бессмысленно. Вернуть в расписание: указать адрес спеки на
вкладке «Настройка» и нажать «Опросить сейчас».

Можно ввести путь — он достроится по адресу опроса — или полный адрес, и тогда
он сохранится целиком, вместе с хостом. Второе нужно, когда документация
отдаётся только через ingress и на backend-порту её нет. Допустимы только два
адреса самого сервиса; чужой хост запрещён — Spectra ходит изнутри кластера, и
такой адрес стал бы способом дотянуться до чего угодно.

## Как считается «последнее обновление»

Опрос — это не обновление. Спека нормализуется, берётся sha256, и ревизия
пишется только при смене хэша.

Нормализация: сортировка ключей объектов и порядконезависимых массивов
(`required`, `enum`, `tags`, `parameters`, `security`), выброс адресов
(`servers`/`host`/`basePath`) и полей из `ignoreFields`. Это важно для сервисов,
перегенерирующих спеку на каждом билде:

| Что меняет генератор | |
|---|---|
| Порядок ключей и элементов массивов | нормализуется всегда |
| Адрес сервиса | `ignoreServers` (по умолчанию) |
| Номер сборки в `info.version` | `ignoreFields: [info.version]` |

Симптом, что настройка нужна: сервис «обновляется» на каждый деплой, а в
изменениях только «изменилась схема данных или описание».

**Откат выкатки** распознаётся по совпадению хэша с прежней ревизией и
помечается как откат, а не как загадочное изменение. Признак «ломающее» при
этом не снимается: тот, кто успел проинтегрироваться с откатываемой версией,
действительно сломается.

## Как считается дифф

Операции сравниваются **с развёрнутыми локальными `$ref`**: правка общей схемы в
`components` не меняет объект операции, но меняет контракт каждого эндпоинта,
который на неё ссылается.

Ломающими помечаются: удалённый эндпоинт, удалённый успешный (2xx) ответ, новый
обязательный параметр, параметр, ставший обязательным, новое обязательное поле в
теле запроса. Список неполный — эвристика привлекает внимание, но как гейт в CI
не годится; для этого берите [oasdiff](https://github.com/Tufin/oasdiff).

## Доступ

**Чтение открыто всем, кто дотянулся до Spectra.** Вместе с публичным адресом
показывается адрес backend-сервиса: когда на одном хосте несколько записей,
различить их иначе нельзя, а сам адрес и так виден любому, у кого есть доступ
к кластеру. Скрыты остаются адрес опроса целиком, имя Ingress, адреса
спецификаций и тексты ошибок.
 Искать документацию по API не
должно требовать логина.

**Всё, что меняет состояние, — под логином** (`SPECTRA_ADMIN_USER` /
`SPECTRA_ADMIN_PASSWORD`). Туда же отнесён прокси: читать документацию можно
всем, слать запросы в API через Spectra — нет.

Неавторизованным не показываются и **не отдаются в API**: внутренние адреса,
backend-сервисы, namespace, имена Ingress, адреса спек, тексты ошибок и журнал
сканирований. Вырезаются на сервере — прятать их в JavaScript бессмысленно,
`/api/services` доступен курлом.

Видны всем: публичный хост, владелец сервиса и дата последней проверки — по ним
человек решает, куда идти и можно ли доверять тому, что перед ним.

# 2. Разворачивание

Подробная инструкция для DevOps — **[deploy/DEPLOY.md](deploy/DEPLOY.md)**.
Коротко:

**Что нужно:** Postgres 13+, ServiceAccount с правом `list` на
`ingresses.networking.k8s.io`, один Deployment. Томов не требуется — всё
состояние в базе, файловая система только для чтения.

**Учётные данные Kubernetes задавать не нужно:** токен и CA монтирует kubelet,
адрес API-сервера приходит в `KUBERNETES_SERVICE_HOST`. Достаточно
`serviceAccountName` в поде.

**Образ** — distroless, статический бинарник, 16 МБ, непривилегированный
пользователь:

```bash
docker build -t spectra:latest .
```

**Масштабирование.** Реплик может быть сколько угодно: опрашивает всегда одна,
её выбирает advisory-lock в Postgres. Без этого три реплики означали бы тройную
нагрузку на каждый опрашиваемый сервис.

**Нагрузка на ваши сервисы.** В установившемся режиме — один условный GET на
сервис в час, сервисы отвечают 304. При первом знакомстве с незнакомым сервисом
— до 45 запросов на перебор адресов, один раз, с паузой между попытками, чтобы
это не выглядело сканированием.

**Наблюдаемость.** `/healthz` для проб, `/metrics` для Prometheus,
структурированные логи в stdout. Алерт, который я бы завёл первым:

```
time() - spectra_discovery_last_success_timestamp_seconds > 3 * 3600
```

Он ловит ситуацию, когда чтение Ingress сломалось, а Spectra продолжает отдавать
закэшированный список — снаружи это никак не заметно.

**Бэкап.** Отдельного состояния нет, подойдёт обычный бэкап базы. Процедура и
восстановление — в [DEPLOY.md](deploy/DEPLOY.md); проверены на живом кластере со
сносом базы целиком.

**CI не настроен.** Тесты и сборка образа запускаются руками; `make test`
поднимает одноразовый Postgres сам, так что перенести это в пайплайн —
несколько строк.

# 3. Разработка

Go 1.25 и Docker. Запускать приложение можно только докером — Go нужен, чтобы
менять код.

```bash
make test        # поднимает одноразовый Postgres и гоняет всё
make test-quick  # без Postgres: тесты, которым он нужен, пропускаются
make demo-up     # стенд целиком
```

## Структура

```
cmd/spectra          бинарь
internal/config      конфигурация из переменных окружения
internal/k8s         дискавери сервисов из Ingress
internal/discovery   поиск спеки у сервиса
internal/openapi     разбор, нормализация, хэш, индекс операций, дифф
internal/collector   опрос по расписанию, запись ревизий
internal/store       Postgres, миграции, настройки
internal/api         HTTP API, метрики, прокси, отдача UI
internal/web         встроенный UI + вендоренный вьюер (Scalar)
demo/                демо-стенд
deploy/              манифесты и инструкция для DevOps
```

Прикладных зависимостей две: `jackc/pgx` и `gopkg.in/yaml.v3`. Kubernetes —
напрямую по HTTP, без client-go: листинг Ingress это один GET, а client-go
добавил бы десятки мегабайт.

## Покрытие тестами

| Пакет | |
|---|---|
| `config` | 93% |
| `openapi` | 80% |
| `k8s` | 76% |
| `api` | 74% |
| `store` | 74% |
| `discovery` | 58% |
| `collector` | 57% |

Тесты `store`, `collector` и `api` идут против **настоящего Postgres** и
настоящих HTTP-серверов. Это не педантизм: половина логики store живёт в SQL, а
половина поведения коллектора — это то, чего он *не* делает (не переопрашивает,
не дублирует ревизии, не накладывает обходы). На моках такое не проверяется.

Почти каждый из этих тестов написан под конкретный найденный дефект — какой
именно, видно в истории коммитов.

## Миграции

`internal/store/migrations/*.sql`, применяются при старте под advisory-lock,
поэтому одновременный запуск нескольких реплик безопасен. Только добавляющие —
откат образа на предыдущую версию не ломает схему.

## Демо-стенд

Семь фейковых сервисов с разными способами публикации спеки плюс граничные
случаи: хост без API, мёртвый backend, ACME-челлендж, wildcard, opt-out,
исключённый namespace, аннотированный сервис. Подробности и что должно
получиться — [deploy/k8s/README.md](deploy/k8s/README.md).

# 4. Командам, ADR, бэклог

## Как команде управлять своим сервисом в Spectra

Аннотации на своём Ingress — без обращения к владельцам портала:

```yaml
metadata:
  annotations:
    spectra.io/skip: "true"            # не индексировать
    spectra.io/name: "Orders API"      # человеческое имя вместо имени Service
    spectra.io/spec-url: /v3/api-docs  # если автопоиск промахивается
    spectra.io/group: "Коммерция"      # группа в списке
    spectra.io/team: "Команда Заказов"
    spectra.io/contact: orders@company.ru
    spectra.io/repo: https://gitlab.company.ru/backend/orders
    spectra.io/owners: ivanov,petrov
```

Либо в самой спецификации — тогда контакты живут рядом с кодом и обновляются
тем же MR:

```yaml
info:
  contact: { name: Команда Заказов, email: orders@company.ru }
  x-repo: https://gitlab.company.ru/backend/orders
externalDocs:
  url: https://gitlab.company.ru/backend/orders
```

Аннотация и спека только **заполняют пустое**: если поле уже вписали руками в
интерфейсе, автоматика его не перезапишет.

Готовые куски кода под l5-swagger, Scribe и springdoc — в
[docs/BACKLOG.md](docs/BACKLOG.md).

## Почему так сделано

**Реестр в базе, а не в git.** В первой версии это был файл под ревью. Как
только список стал приходить из кластера и настраиваться в интерфейсе, он стал
изменяемым состоянием. Платим тем, что изменения реестра больше не проходят
ревью.

**Postgres, а не SQLite.** Реестр изменяемый, процесс должен быть stateless и
переживать несколько реплик.

**Опрашивает одна реплика.** Выбирается advisory-lock. Spectra — гость на чужой
инфраструктуре и не должна быть причиной роста трафика у сервисов.

**Env и база делят настройки.** В окружении — всё, без чего не стартовать; в
базе — всё, что крутят в рантайме. Страница настроек и неизменяемое окружение не
могут владеть одним значением.

**Kubernetes по HTTP, без client-go.** Листинг Ingress — один GET к
документированному стабильному API. client-go добавил бы десятки мегабайт,
kubectl потребовал бы отказаться от distroless.

**Страница документации ищется раньше конвенциональных путей.** Наблюдение с
реальной инфраструктуры: JSON лежит где угодно, а `/swagger` есть почти везде.

**Свой дифф вместо oasdiff.** Внешний бинарник в рантайме ради «привлечь
внимание» — лишняя зависимость. Платим неполнотой покрытия.

**Ручной ввод владельца — основной путь, а не запасной.** В свежей установке
контактов нет нигде, поэтому фильтр «без владельца» и надпись «владелец не
указан» важнее автоматических источников: невидимый пробел не закроется.

## Чего пока нет

Отложенное с уже принятыми решениями — в **[docs/BACKLOG.md](docs/BACKLOG.md)**,
чтобы разбор не пришлось проводить заново. Коротко:

- Пайплайна CI.
- Уведомлений о ломающих изменениях (`breaking` в таблице `changes` уже есть).
- Поиска по эндпоинтам через все сервисы.
- Журнала действий администратора: кто и когда спрятал сервис или указал адрес.
- Аутентификации сложнее Basic — предполагается SSO впереди.
- Проверки под реальной нагрузкой: гонялось на 11 сервисах, не на 200.
